1. Cel i kontekst biznesowy stable

4.5 solution_chunks — jednostka wyszukiwania

Wyszukujemy po fragmentach, nie po całych rozwiązaniach. Dwa pola denormalizowane (title, published) — powody w ostrzeżeniu pod DDL, nie usuwaj ich.

CREATE TABLE solution_chunks (
    id          BIGSERIAL PRIMARY KEY,
    solution_id BIGINT NOT NULL REFERENCES solutions(id) ON DELETE CASCADE,
    chunk_index INT    NOT NULL,
    title       TEXT   NOT NULL,              -- kopia solutions.title (denormalizacja)
    heading     TEXT,                         -- nagłówek sekcji wewnątrz dokumentu
    content     TEXT   NOT NULL,
    published   BOOLEAN NOT NULL DEFAULT true,-- kopia (solutions.status = 'PUBLISHED')
    embedding   vector(1024),                 -- NULL dopóki nie policzony
    ts          tsvector GENERATED ALWAYS AS (
                    setweight(to_tsvector('polish_simple', coalesce(title, '')),   'A') ||
                    setweight(to_tsvector('polish_simple', coalesce(heading, '')), 'B') ||
                    setweight(to_tsvector('polish_simple', content),               'C')
                ) STORED,
    UNIQUE (solution_id, chunk_index)
);

CREATE INDEX solution_chunks_ts_idx ON solution_chunks USING gin (ts);

CREATE INDEX solution_chunks_emb_idx ON solution_chunks
    USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64)
    WHERE published;

Dlaczego title jest kopiowane do chunku. Kolumna GENERATED ALWAYS AS może czytać wyłącznie kolumny tego samego wiersza — nie wolno jej sięgnąć do solutions joinem. Bez kopii tytułu tracisz wagę A, a tytuł jest najsilniejszym sygnałem leksykalnym w całym korpusie.

Dlaczego published jest kopiowane. Indeks HNSW działa tylko wtedy, gdy zapytanie ma postać ORDER BY embedding <=> $1 LIMIT n bez joinów. Filtr solutions.status w WHERE wymusiłby pełny skan. Indeks częściowy WHERE published rozwiązuje to w całości. Oba pola aktualizuje ingest oraz zmiana statusu rozwiązania — spakuj to w jedną funkcję sync_chunk_denorm(solution_id), nie rozsiewaj po kodzie.

Strategia chunkowania

  • chunk_index = 0 — zawsze title + "\n" + summary. To jest chunk, który trafia w większość zapytań.
  • chunk_index >= 1 — body pocięte po akapitach do ~1200 znaków, z zakładką ~150 znaków, granice na końcach zdań.
  • Krótkie rozwiązanie (body pusty lub poniżej 400 znaków) ma dokładnie jeden chunk. Nie wymuszaj sztucznego cięcia.

5. Polski tor leksykalny stable

Przeczytaj przed napisaniem pierwszego to_tsvector. PostgreSQL nie ma konfiguracji polish w standardowej instalacji ani w obrazie pgvector/pgvector:pg16. Zapis to_tsvector('polish', ...) wywali się błędem text search configuration "polish" does not exist. Nie obchodź tego przez 'english' — angielski stemmer na polszczyźnie psuje więcej, niż naprawia.

Rozwiązanie w v0.1: własna konfiguracja polish_simple — simple (bez stemmingu) plus unaccent (usuwa ogonki, więc „dzieci" i „dzięci" czy brak polskich znaków w zapytaniu przestają mieć znaczenie).

CREATE TEXT SEARCH CONFIGURATION polish_simple ( COPY = simple );

ALTER TEXT SEARCH CONFIGURATION polish_simple
    ALTER MAPPING FOR word, hword, hword_part, asciiword, asciihword, hword_asciipart
    WITH unaccent, simple;

-- opcjonalnie: lista stopwords, znacząco podnosi precyzję ts_rank_cd
-- plik $SHAREDIR/tsearch_data/polish_simple.stop + ALTER ... WITH unaccent, simple;

Dlaczego to działa w kolumnie generowanej. Funkcja unaccent() sama jest STABLE, co normalnie dyskwalifikuje ją z GENERATED ALWAYS AS. Ale dwuargumentowe to_tsvector(regconfig, text) jest IMMUTABLE — i to ono, nie unaccent, stoi w definicji kolumny. Dlatego konfiguracja musi być podana jawnie jako literał ('polish_simple'), nigdy przez default_text_search_config.

Cena braku stemmingu i jak ją spłacamy

simple nie skleja „samotność" z „samotnością" ani „senior" z „seniorzy". Trzy mechanizmy kompensujące, wszystkie już w architekturze:

  1. Tor semantyczny — odmiana fleksyjna nie ma wpływu na embedding. To główny amortyzator i jeden z powodów, dla których architektura jest hybrydowa.
  2. pg_trgm na tytułach — podobieństwo trigramowe łapie wspólny rdzeń niezależnie od końcówki, także literówki.
  3. Rozszerzanie zapytania w preprocessingu — mały słownik ręczny dla terminów domenowych (senior → senior, seniorzy, starszy, 65+), plik data/synonyms.json, doklejane do tsquery jako alternatywy OR.

6.1 Preprocessing

Wejście: surowy tekst użytkownika. Wyjście: ProcessedQuery.

@dataclass
class ProcessedQuery:
    raw: str                      # zachowane dosłownie, idzie do reports.raw_text
    normalized: str               # do embeddingu i tsquery
    gmina: str | None
    powiat: str | None
    category: str | None          # kod z challenge_taxonomy
    target_group: str | None
    identifiers: list[str]        # nazwy własne, akronimy, numery uchwał

Kolejność operacji:

  1. Normalizacja — NFC, zbicie białych znaków, obcięcie do 2000 znaków.
  2. Zdjęcie wstępów grzecznościowych — regex na ^(cześć|dzień dobry|witam|hej|dobry wieczór|szanowni państwo)[,!.\s]*, rekurencyjnie. Zdejmowane tylko z normalized; raw zostaje nietknięty.
  3. Ekstrakcja gminy i powiatu — dopasowanie do słownika data/gminy-malopolska.json (182 gminy, 22 powiaty, w tym formy odmienione: Zakopane / w Zakopanem, Nowy Sącz / w Nowym Sączu). Dopasowanie po tekście unaccent-owanym i lowercase. Zbudowany raz jako automat Aho-Corasick lub prosty zbiór n-gramów — nie regex per gmina.
  4. Ekstrakcja identyfikatorów — wyrazy w CAPS (3+ znaki), ciągi alfanumeryczne z cyfrą, nazwy w cudzysłowie, frazy wielkolitrowe wielowyrazowe. Trafiają do tsquery z operatorem frazowym, żeby tor leksykalny ich nie zgubił.
  5. Kategoria — słownik słów kluczowych per kod taksonomii (samotn*, izolacj*, sam w domu → LONELINESS). Gdy LLM_ENABLED=true i słownik nie trafia: jedno wywołanie klasyfikatora zwracającego wyłącznie kod. Gdy nic — OTHER, nie wymyślaj.
  6. Rozszerzenie synonimami — data/synonyms.json, tylko dla toru leksykalnego.
  7. Detekcja zbyt ogólnego zapytania — too_vague ustawiany, gdy po usunięciu stopwords zostają mniej niż 4 wyrazy treściowe. Pipeline mimo to leci dalej; flaga tylko dodaje do odpowiedzi prośbę o doprecyzowanie.

Pułapka. Nie przycinaj zapytania do słów kluczowych. Tor semantyczny potrzebuje pełnych zdań — wektor z „starsi ludzie siedzą sami w domach" jest znacznie trafniejszy niż z „starsi ludzie dom". Preprocessing dodaje metadane, nie odbiera treści.

6.2 Tor leksykalny — PostgreSQL FTS

Wejście: normalized + identifiers + expanded_terms. Wyjście: do 20 par (solution_id, best_chunk_id) uszeregowanych po ts_rank_cd.

Budowa tsquery: websearch_to_tsquery dla tekstu swobodnego, do tego identyfikatory jako frazy i synonimy jako alternatywy:

-- :tsq_text  = normalized
-- :tsq_extra = '"ERR_CONN_REFUSED" | senior | seniorzy'   (zbudowane w Pythonie, escapowane)
SELECT
    websearch_to_tsquery('polish_simple', :tsq_text)
    || to_tsquery('polish_simple', :tsq_extra)   AS tsq;
WITH q AS (
    SELECT websearch_to_tsquery('polish_simple', :query_text) AS tsq
),
hits AS (
    SELECT DISTINCT ON (c.solution_id)
           c.solution_id,
           c.id                                  AS chunk_id,
           ts_rank_cd(c.ts, q.tsq, 32)           AS score
    FROM solution_chunks c
    CROSS JOIN q
    WHERE c.published
      AND c.ts @@ q.tsq
    ORDER BY c.solution_id, score DESC          -- najlepszy chunk na rozwiązanie
)
SELECT solution_id, chunk_id, score,
       ROW_NUMBER() OVER (ORDER BY score DESC, solution_id) AS rnk
FROM hits
ORDER BY score DESC, solution_id
LIMIT :candidates_per_track;                     -- 20

ts_rank_cd(..., 32) — normalizacja 32 to rank/(rank+1), skaluje wynik do przedziału 0–1. Dla RRF jest to bez znaczenia (liczy się tylko pozycja), ale ułatwia debugowanie w /api/search.

Pułapka. DISTINCT ON wymaga, by ORDER BY zaczynał się od kolumny wyrażenia DISTINCT ON. Dlatego kolaps per rozwiązanie i ranking globalny muszą być w dwóch osobnych poziomach zapytania, jak wyżej. Jedno zapytanie nie zrobi obu rzeczy.

6.3 Tor semantyczny — pgvector HNSW

Wejście: normalized. Wyjście: do 20 par (solution_id, best_chunk_id) po odległości cosinusowej.

Prefiksy zapytań — pole konfiguracji, nie stała w kodzie

Modele z rodzin E5 i BGE były trenowane z asymetrycznymi prefiksami: zapytanie query: ..., dokument passage: .... Modele OpenAI prefiksów nie używają i doklejenie ich pogarsza wyniki. Dlatego prefiks należy do providera:

class EmbeddingProvider(Protocol):
    dim: int                 # MUSI być 1024 dla każdej implementacji, patrz ADR-004
    query_prefix: str        # "query: " dla bge-m3/e5, "" dla OpenAI
    passage_prefix: str      # "passage: " dla bge-m3/e5, "" dla OpenAI

    async def embed_query(self, text: str) -> list[float]: ...
    async def embed_passages(self, texts: list[str]) -> list[list[float]]: ...

Najkosztowniejszy możliwy błąd w tym module: zaindeksować korpus jednym providerem, a zapytania liczyć drugim, albo doklejać prefiks tylko w jednym miejscu. Wyniki nie wywalą błędu — po prostu będą ciche i bezsensowne. Zabezpieczenia, oba obowiązkowe:

  • Tabela embedding_meta (jeden wiersz: provider, model, dim, indexed_at). Start API porównuje ją z konfiguracją i odmawia startu przy rozbieżności, z komunikatem „uruchom scripts/reembed.py".
  • Prefiksy doklejane wyłącznie wewnątrz implementacji providera. Żaden kod pipeline'u nie zna słowa "query: ".

Zapytanie

-- Nadpobranie: wiele chunków może należeć do jednego rozwiązania,
-- więc 20 chunków nie da 20 różnych rozwiązań.
WITH raw AS (
    SELECT c.id AS chunk_id, c.solution_id,
           c.embedding <=> CAST(:query_vec AS vector(1024)) AS dist
    FROM solution_chunks c
    WHERE c.published
      AND c.embedding IS NOT NULL
    ORDER BY c.embedding <=> CAST(:query_vec AS vector(1024))
    LIMIT :vector_overfetch                      -- 60 = 3 x candidates_per_track
),
best AS (
    SELECT DISTINCT ON (solution_id) solution_id, chunk_id, dist
    FROM raw
    ORDER BY solution_id, dist
)
SELECT solution_id, chunk_id, dist,
       1.0 - dist                                AS cosine_similarity,
       ROW_NUMBER() OVER (ORDER BY dist, solution_id) AS rnk
FROM best
ORDER BY dist, solution_id
LIMIT :candidates_per_track;                      -- 20

Pułapki toru wektorowego.

  • <=> to odległość cosinusowa (0 = identyczne). Podobieństwo to 1 - dist. Sortowanie zawsze ASC po dist.
  • ORDER BY w raw musi być dosłownie identycznym wyrażeniem co w SELECT, inaczej planer nie użyje HNSW. Sprawdź EXPLAIN — ma pokazać Index Scan using solution_chunks_emb_idx, nie Seq Scan.
  • SET hnsw.ef_search = 100; na połączeniu przed zapytaniem (domyślne 40 jest niskie dla małego korpusu). Ustawiaj per sesja w kodzie, nie globalnie.
  • Żadnych dodatkowych warunków WHERE w raw poza tymi z indeksu częściowego — każdy dodatkowy filtr psuje użycie indeksu.

6.4 Fuzja — Reciprocal Rank Fusion

Wejście: dwie listy po maks. 20 pozycji. Wyjście: 10 kandydatów.

Oceny ts_rank_cd i podobieństwa cosinusowego mają nieporównywalne skale, więc nie wolno ich sumować ani normalizować min-max (ta druga metoda jest niestabilna, bo zależy od przypadkowego najlepszego wyniku w partii). RRF punktuje wyłącznie pozycje:

RRF(d) = Σ   1 / (k + rank_m(d))        k = 60
        m∈M

Implementacja w Pythonie (listy są już w pamięci — osobny round-trip do bazy jest zbędny):

def rrf_fuse(
    tracks: dict[str, list[Candidate]],
    k: int = 60,
    top_n: int = 10,
) -> list[FusedCandidate]:
    scores: dict[int, float] = defaultdict(float)
    ranks:  dict[int, dict[str, int]] = defaultdict(dict)
    chunks: dict[int, int] = {}

    for track_name, candidates in tracks.items():
        for rank, cand in enumerate(candidates, start=1):   # 1-indeksowane
            scores[cand.solution_id] += 1.0 / (k + rank)
            ranks[cand.solution_id][track_name] = rank
            # chunk z toru wektorowego preferowany jako kontekst dla rerankera
            if cand.solution_id not in chunks or track_name == "semantic":
                chunks[cand.solution_id] = cand.chunk_id

    ordered = sorted(scores.items(), key=lambda kv: (-kv[1], kv[0]))
    return [
        FusedCandidate(
            solution_id=sid, chunk_id=chunks[sid],
            rrf_score=score, ranks=ranks[sid],
        )
        for sid, score in ordered[:top_n]
    ]

Przykład liczbowy

Rozwiązanie „Telefon Życzliwości — wsparcie telefoniczne dla seniorów" wypada na pozycji 1 w torze leksykalnym (trafione słowa senior, telefon) i na pozycji 4 w torze semantycznym (kontekst samotności):

RRF = 1/(60+1) + 1/(60+4) = 0.01639 + 0.01563 = 0.03202

Rozwiązanie widoczne tylko w jednym torze, nawet na pozycji 1, dostaje 0.01639. Zgoda dwóch torów bije świetny wynik w jednym — to cała istota RRF.

Dlaczego k = 60 i kiedy to zmieniać. Duże k wygładza różnice między pozycjami (pozycja 1 i 5 dostają podobnie), małe k mocno premiuje czoło listy. 60 to wartość z oryginalnej pracy i dobry punkt startu. Zmieniaj tylko na podstawie make eval (sekcja 10), nigdy na podstawie pojedynczego zapytania, które „wygląda źle".

Determinizm: przy identycznym rrf_score sortuj po solution_id rosnąco. Bez tego kolejność wyników skacze między wywołaniami, a zestaw ewaluacyjny przestaje być powtarzalny.

6.5 Reranking — cross-encoder

Wejście: 10 kandydatów + zapytanie. Wyjście: 1–3 pozycje ze score 0–1.

RRF zna tylko pozycje, nie treść. Cross-encoder czyta parę (zapytanie, dokument) razem i ocenia realną relację semantyczną — jest znacznie dokładniejszy niż niezależne embeddingi, ale zbyt kosztowny dla całego korpusu. Dlatego jest na końcu, na dziesięciu pozycjach.

6.7 Zapis zgłoszenia i klastrowanie

Wejście: ProcessedQuery + embedding + wynik dopasowania. Wyjście: report_id, cluster_id.

Zapis jest bezwarunkowy — także gdy nie znaleziono rozwiązania, i także gdy użytkownik zamknie kartę w połowie strumienia. Uruchamiany jako zadanie w tle, równolegle z generacją; porażka zapisu nie może przerwać odpowiedzi (log + metryka, nie wyjątek do użytkownika).

Klastrowanie przyrostowe (single-pass, próg stały)

-- 1. najbliższy klaster
SELECT id, member_count, 1.0 - (centroid <=> CAST(:vec AS vector(1024))) AS similarity
FROM report_clusters
ORDER BY centroid <=> CAST(:vec AS vector(1024))
LIMIT 1;
-- 2a. similarity >= CLUSTER_SIM_THRESHOLD (0.82) -> dopnij, przelicz centroid
UPDATE report_clusters
SET centroid     = (centroid * member_count + CAST(:vec AS vector(1024)))
                   / (member_count + 1),
    member_count = member_count + 1,
    gminas       = CASE WHEN :gmina IS NULL OR :gmina = ANY(gminas)
                        THEN gminas ELSE array_append(gminas, :gmina) END,
    last_seen_at = now()
WHERE id = :cluster_id
RETURNING id;

-- 2b. w przeciwnym razie -> nowy klaster
INSERT INTO report_clusters (label, category, centroid, member_count, gminas)
VALUES (left(:normalized_text, 160), :category,
        CAST(:vec AS vector(1024)), 1,
        CASE WHEN :gmina IS NULL THEN '{}' ELSE ARRAY[:gmina] END)
RETURNING id;

Trzy rzeczy, które trzeba zrobić dobrze.

  • Normalizacja L2. Centroid po średniej arytmetycznej nie ma długości 1. Przy odległości cosinusowej pgvector normalizuje wewnętrznie, więc ranking jest poprawny, ale wartość 1 - dist przestaje być porównywalna z progiem w kolejnych aktualizacjach. Normalizuj wektory zgłoszeń przed zapisem i centroid po każdej aktualizacji.
  • Wyścig. Dwa równoległe zgłoszenia o tym samym problemie przy pustej bazie utworzą dwa klastry. Owiń odczyt i zapis w transakcję z SELECT ... FOR UPDATE na znalezionym klastrze, a przy jego braku użyj blokady doradczej pg_advisory_xact_lock na stałym kluczu. Dla hackathonu wystarczy, ale nie pomijaj — demo z dwoma osobami klikającymi równocześnie to realny scenariusz.
  • Próg 0.82 jest zgadywany. Skalibruj na realnych zgłoszeniach: za nisko — wszystko zlewa się w jeden klaster „problemy społeczne"; za wysoko — każde zgłoszenie jest własnym klastrem i licznik skali traci sens. Skrypt scripts/cluster_report.py wypisujący rozkład rozmiarów klastrów dla kilku progów to 30 linii kodu i ratuje całą sekcję.

Nazwa klastra. W v0.1 — obcięty tekst pierwszego zgłoszenia (label_source = 'FIRST_REPORT'). Operator może nadpisać ('OPERATOR'). Generowanie nazwy przez LLM z kilku zgłoszeń: Moduł 2.

  1. Wczytaj i zwaliduj po schemacie Pydantic. Błędny rekord: pomiń, wypisz powód, nie przerywaj całej partii.
  2. content_hash = sha256(title + summary + body).

  4. Hash niezmieniony ⇒ pomiń chunkowanie i embedding. To cała istota idempotencji — ponowne uruchomienie na 500 wpisach po dopisaniu jednego nie może kosztować 500 wywołań API.

  6. Zsynchronizuj published i title we wszystkich chunkach (sync_chunk_denorm).
  7. Zapisz embedding_meta (provider, model, dim, indexed_at).

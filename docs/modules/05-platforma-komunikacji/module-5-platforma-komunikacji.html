1. Cel i kontekst biznesowy stable

Wymaganie z base.md (V)

Zintegrowany system pozwalający na bezpośredni dialog między ROPS Kraków a użytkownikami, ułatwiający szybkie zadawanie pytań, otrzymywanie wsparcia od mentorów oraz budowanie międzysektorowych partnerstw.

Cel w jednym zdaniu

Każda rozmowa z Hubem — pytanie, zgłoszenie, prośba o eksperta, propozycja partnerstwa — toczy się w jednym wątku, w którym AI odpowiada od razu z bazy rozwiązań, a człowiek (pracownik Hubu albo mentor) przejmuje rozmowę, gdy AI nie wystarcza.

3. Zakres MVP i granice stable

W PoC

  1. Wątki czterech rodzajów: QUESTION (pytanie do Hubu), REPORT (rozmowa przy zgłoszeniu z Modułu 1), MENTORING (prośba o eksperta), PARTNERSHIP (propozycja współpracy do ogłoszenia).
  2. Asystent pierwszego kontaktu — automatyczna odpowiedź AI na nowe pytanie (QUESTION), z kartami rozwiązań; „To mi pomogło” / „Chcę porozmawiać z zespołem Hubu”.

  6. Powiadomienia w aplikacji: liczniki w panelu, „nowa odpowiedź” w „Moich rozmowach”, SLA (czas oczekiwania).

Scenariusz A — pytanie z natychmiastową odpowiedzią (scenariusz demo, ~60 s)

  1. Pani Ewa z GOPS (konto reporter) wchodzi w „Platforma komunikacji” → „Zadaj pytanie”: „Jak zorganizować dowóz seniorów do lekarza w gminie wiejskiej?”.
  2. Widzi swój wątek i komunikat „Asystent szuka odpowiedzi w Bibliotece Innowacji…”. Po kilku sekundach pojawia się wiadomość oznaczona „Odpowiedź automatyczna (AI)” z cytowaniami [1], [2] i kartami rozwiązań.
  3. Klika „Chcę porozmawiać z zespołem Hubu” → status „Czeka na zespół Hubu”.
  4. Pracownik ROPS (konto admin) widzi licznik w panelu („Rozmowy 1”), otwiera wątek, klika „Podpowiedz odpowiedź (AI)”, poprawia szkic, przypina kartę rozwiązania i wysyła. Przydziela eksperta z listy podpowiedzi („Kategoria: Dostęp do usług · podobieństwo 71%”).
  5. Ekspert (konto ekspert) widzi rozmowę w „Moje konsultacje” i dopisuje radę.
  6. Pani Ewa w „Moich rozmowach” widzi oznaczenie „Nowa odpowiedź” i czyta obie wiadomości.

Scenariusz B — autor zgłoszenia odpisuje Hubowi

  1. Autor zgłoszenia z Modułu 1 w „Moich zgłoszeniach” widzi odpowiedź zespołu (F12) i klika „Odpisz”.
  2. Powstaje (albo otwiera się istniejący) wątek REPORT; oś czasu pokazuje dotychczasowe odpowiedzi z report_replies i nową wiadomość autora.
  3. Pracownik widzi wątek w „Rozmowach” i w szczegółach zgłoszenia (link „Rozmowa z autorem”).

Scenariusz C — partnerstwo międzysektorowe

  1. Fundacja (NGO) publikuje ogłoszenie „Szukamy gminy do pilotażu teleopieki”. Trafia do moderacji; pracownik zatwierdza.
  2. Na stronie ogłoszenia: „Pasujące ogłoszenia” (np. gmina oferująca lokal i kadrę — oznaczenie „międzysektorowe”), „Powiązane rozwiązania z Biblioteki”, „Zapotrzebowanie: 7 podobnych zgłoszeń problemów”.
  3. Gmina klika „Zaproponuj współpracę” → wątek PARTNERSHIP; Hub pośredniczy i przekazuje kontakt obu stronom poza platformą.

CREATE TYPE thread_kind        AS ENUM ('QUESTION', 'REPORT', 'MENTORING', 'PARTNERSHIP');
CREATE TYPE thread_status      AS ENUM ('ASSISTANT_PENDING', 'ANSWERED_BY_AI', 'WAITING_STAFF', 'WAITING_USER', 'CLOSED');
CREATE TYPE message_role       AS ENUM ('USER', 'STAFF', 'MENTOR', 'ASSISTANT', 'SYSTEM');
CREATE TYPE org_sector         AS ENUM ('NGO', 'JST', 'PUBLIC', 'BUSINESS', 'SCIENCE', 'RESIDENTS');
CREATE TYPE partnership_intent AS ENUM ('OFFER', 'SEEK');
CREATE TYPE offer_status       AS ENUM ('PENDING_REVIEW', 'PUBLISHED', 'REJECTED', 'CLOSED');

-- Eksperci / mentorzy (dane fikcyjne z data/mentors.json).

    seed_key     TEXT UNIQUE,                      -- idempotencja seeda

-- Ogłoszenia partnerstw (tablica „oferuję / szukam”).

-- Wątki rozmów (jeden model dla pytań, zgłoszeń, mentoringu i partnerstw).

    user_last_read_at   TIMESTAMPTZ,
    staff_last_read_at  TIMESTAMPTZ,
    mentor_last_read_at TIMESTAMPTZ,
    created_at          TIMESTAMPTZ   NOT NULL DEFAULT now(),

CREATE INDEX threads_status_idx ON threads (status, last_message_at DESC);
CREATE INDEX threads_mentor_idx ON threads (assigned_mentor_id, last_message_at DESC);

CREATE TABLE thread_messages (
    id           BIGSERIAL PRIMARY KEY,
    thread_id    BIGINT       NOT NULL REFERENCES threads(id) ON DELETE CASCADE,
    role         message_role NOT NULL,
    author_label TEXT,
    mentor_id    BIGINT       REFERENCES mentors(id) ON DELETE SET NULL,

7. Logika i AI draft

7.1 Po utworzeniu wątku (api.comm.threads.after_create, w tle przez spawn)

  1. Własna sesja z SessionLocal() (zadanie odpięte od żądania, jak zapis zgłoszenia w M1).
  2. Embedding subject + "\n" + body przez embed_query → threads.embedding. Błąd providera → NULL (sugestie ekspertów działają wtedy po samej kategorii).
  3. Gdy kind = QUESTION i status ASSISTANT_PENDING → run_assistant(thread_id).
  4. notify("thread_created", thread_id).

Kategoria wątku liczona synchronicznie przy tworzeniu: preprocess(body, None).category (słowa kluczowe M1, bez LLM), chyba że klient podał category.

7.2 Asystent pierwszego kontaktu (api.comm.assistant.run_assistant)

  1. q = preprocess(first_user_body, None); result = await run_search(q) (reranker opcjonalny, bramka „nie wiem” działa na cosinusie).
  2. Bramka nie przeszła albo result.solutions puste → wiadomość SYSTEM „Nie mam gotowej odpowiedzi w Bibliotece Innowacji. Pytanie trafiło do zespołu Hubu — odpowiemy w tym wątku.”, status WAITING_STAFF.
  3. Karty = result.solutions (≤ ANSWER_TOP_N, tylko SOLUTION; KNOWLEDGE nigdy). Gdy LLM_ENABLED: zbierz generate(q.normalized, cards, result.best_chunks, q.too_vague, llm) przez CitationFilter(len(cards)), limit czasu ASSISTANT_TIMEOUT_SECONDS. filter.should_retract → tekst odrzucony (meta.retracted = true).
  4. Brak LLM / błąd / odrzucenie → treść zastępcza „Te rozwiązania z Biblioteki Innowacji mogą pomóc:” (meta.fallback = "no_llm" | "error" | "retracted"). Moduł działa bez AI.
  5. Zapis wiadomości ASSISTANT z solution_ids w kolejności kart (cytowanie [n] = pozycja n), meta.gate = {source, score, threshold}; status ANSWERED_BY_AI.
  6. Wyjątek w zadaniu → status WAITING_STAFF + wiadomość SYSTEM; wątek nigdy nie zostaje w ASSISTANT_PENDING (zabezpieczenie w finally).

7.3 Szkic odpowiedzi dla pracownika (api.comm.assistant.draft_reply)

  • Zapytanie = ostatnia wiadomość USER (albo subject). run_search → karty → LLM z promptem DRAFT_SYSTEM.
  • DRAFT_SYSTEM (instrukcje tylko w system, treść użytkownika jako blok danych): „Piszesz szkic odpowiedzi pracownika Małopolskiego Hubu Innowacji Społecznych do mieszkańca lub instytucji. Opieraj się wyłącznie na rozwiązaniach z kontekstu, każde twierdzenie opatrz [n]. Maks. 6 zdań, uprzejmie, prostym językiem. Nie obiecuj terminów, finansowania ani decyzji. Jeśli kontekst nie pasuje — zaproponuj jedno pytanie doprecyzowujące.”
  • Wynik: DraftReply {body, solution_ids, cards}. Nie zapisywany; pracownik edytuje i wysyła zwykłą wiadomością STAFF (może dołączyć solution_ids).
  • LLM_ENABLED=false lub DRAFT_REPLY_ENABLED=false → 503 LLM_UNAVAILABLE; interfejs ukrywa wtedy przycisk po pierwszym 503.

7.4 Podpowiedź eksperta (api.comm.matching.suggest_mentors)

  • Kandydaci: mentors.active. Dla każdego: category_match = thread.category = ANY(mentor.categories), similarity = 1 - (mentor.embedding <=> thread.embedding) (gdy oba niepuste).
  • Filtr: category_match OR similarity ≥ MENTOR_MIN_COSINE. Sortowanie: category_match DESC, similarity DESC NULLS LAST, id ASC. Limit MENTOR_SUGGEST_N. Nie sumujemy kategorii i cosinusa w jeden wynik.
  • Embedding eksperta: embed_passages na expertise + bio + etykiety kategorii (przy seedzie).

7.5 Dopasowanie partnerstw (api.comm.matching.match_partners)

  • Ogłoszenia: status = PUBLISHED, id ≠ offer.id, intent ≠ offer.intent (oferta ↔ poszukiwanie), similarity ≥ PARTNER_MIN_COSINE; sort similarity DESC, id ASC; limit PARTNER_MATCH_N; cross_sector = sector ≠ offer.sector.
  • Rozwiązania: semantic_search(session, offer.embedding, kind="SOLUTION", limit=PARTNER_SOLUTIONS_N), filtr cosine ≥ MIN_COSINE_SCORE → karty.
  • Zapotrzebowanie: liczba zgłoszeń z reports o 1 - (embedding <=> offer.embedding) ≥ SIMILAR_REPORT_THRESHOLD + top PARTNER_GMINY_N gmin (tylko niepuste). Agregat — bez treści zgłoszeń.
  • Embedding ogłoszenia liczony przy tworzeniu (embed_passages, w tle przez spawn); bez embeddingu → puste dopasowania, nie błąd.

7.6 Powiadomienia (api.comm.threads.notify)

Punkt integracji: notify(event, thread_id) loguje zdarzenie (thread_created, message_created, status_changed, mentor_assigned) z identyfikatorami, rolą i długością treści — bez treści. W PoC powiadomienie „widzi” użytkownik przez liczniki i znaczniki „nowa odpowiedź” (polling). E-mail i webhook podłączamy później w tym jednym miejscu (backlog).

11. RODO i bezpieczeństwo stable

  • Dane osobowe: contact_email (wątki, ogłoszenia) — opcjonalne, nigdy w odpowiedziach API ani w logach; serializacja z jawnej listy kolumn. author_label — wolny tekst, w interfejsie podpowiedź „Nie podawaj nazwiska, jeśli nie chcesz”.
  • Logi: tylko identyfikatory, rodzaj, status, rola, długości (body_len). api/log.py dostaje w REDACTED_KEYS także body, subject, description, author_label (ADR-M5-010).
  • Kontakt w partnerstwach pośredniczony: ogłoszenie pokazuje organizację i sektor, nie osobę; kontakt przekazuje Hub w wątku PARTNERSHIP (ADR-M5-007).
  • Przejrzystość AI: wiadomości AI zawsze role = ASSISTANT i podpis „Odpowiedź automatyczna (AI)”; szkic pracownika nigdy nie wychodzi bez jego akcji (ADR-M5-005).
  • Prompt injection: treść użytkownika tylko jako blok danych w wiadomości user, instrukcje wyłącznie w system; zmyślone [n] wycina CitationFilter.
  • Bez autoryzacji (PoC): wątki są czytelne po id, role wybiera klient. Ryzyko opisane w ADR-M5-003; dane demo są fikcyjne (base.md §9).
